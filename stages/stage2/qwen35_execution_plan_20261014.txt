## 3. 允许最终响应解释，统一答案解析

生成器继续 enable_thinking=True。删除旧“最终只能输出一行”的硬性提示和为这一要求添加的简单算术 few-shot；使用问题原文与固定提示，不改写题目数学内容。

生成器 system prompt 固定为：

~~~text
Solve the mathematical problem carefully. You may explain your solution in the final response.
End the final response with exactly one line in this format:
Final answer: \boxed{answer}
Place no text after that line.
~~~

原生 chat template 保留；不强迫模型在 Thinking 中写 Step 1、Step 2。生成器采样保持 do_sample=True、temperature=1.0、top_p=0.95、top_k=20、min_p=0.0、presence_penalty=1.5、repetition_penalty=1.0，记录处理器实际生效情况。

Stage2 的 grade 与 Stage3 的 terminal 复用同一套最终答案提取：
1. 去掉已知 EOS 控制尾缀，保留全部原始 token 与原文；要求生成正常 EOS、原生 Thinking 正常关闭。
2. 只在关闭 Thinking 后的最终响应中寻找独立的 Final answer 行。
3. 必须恰好一行，且是最后一个非空行；该行除固定前缀、一个完整 \boxed{...} 与空白外无其他文字，使用现有括号解析以支持 \frac 等嵌套表达式。
4. 允许这一行前有解释和计算；不在 Thinking、解释中的其他 boxed 或多个冲突 Final answer 中挑选答案。
5. Math-Verify 只评分该行的答案。Stage3 终点验证仍检查完整有效推理与最终响应，不能只看该行。

加入 final_response_mode="explanation_then_final_line" 到两份新配置，旧配置默认保持原来的解析方式。只增加这一必要分支，不扩展为通用格式系统。

格式错误、标准答案解析失败、预测答案解析失败、超时和输出截断分别记录。缺少最终答案不能靠补 </think>、猜答案或从内部草稿抓 boxed 来修补。

因提示词和预算变化，旧轨迹只作诊断；新正式 run 不导入旧 tokens/特征。若离线重评分旧记录，另存诊断结果，不覆盖原记录或混进正式数据。

## 4. 生成器预算与新 smoke

将单次生成上限从 32768 提高到 81920 token；生成器总上下文上限设为 131072 token，包含题目、历史、反馈和新输出。不启用 YaRN。

81920 依据官方复杂竞赛数学建议，是这一轮固定资源预算，不保证题题完成。不能对失败题临时放宽，不改变种子重复抽到满意轨迹，不挑能完成的替代题。

只在配置字段中设置预算，沿用现有逐 token 生成和分块 prefill。prefill_chunk_size 起步保持 2048；确因临时显存不足，可在正式采集前试 1024，再固定有效值。预算扩大后的长前缀 hidden 提取也必须检查，不能只检查 decode。

重新运行原固定顺序的 10 道 smoke，每题一条轨迹。报告 EOS、截断、解析异常、可评分数、候选位置数量、最长位置间隔、输出 token、生成/提取时间和显存。

用这 10 题的实际生成加特征提取耗时估算 300 题的 GPU 时间，并报告截断长题对估算的影响。独立前缀重前向可能很贵，应先给出实测成本；本轮不为省时间静默改成另一种 hidden 特征。

启动正式 Stage2 的最低条件：
- 必要的 token 对齐、因果/特征、暂停恢复检查通过；复用已有检查，只重跑受代码与新预算影响的部分。
- 至少 8/10 题正常完成且具有可解析最终答案。可解析不要求答案正确。
- 记录并检查最长完成前缀的 hidden 提取；没有未解释的显存错误。
- 不依据 smoke 数学正确率挑提示或题目。

8/10 是本实验预定的工程条件，不是模型能力认证。未过时完成并保存诊断，区分“未结束”“没有最终标记”“无法解析”等原因；停止正式 Stage2 的启动，不再把问题笼统标成等待格式许可。原格式修改已在本方案授权。

不得用提前停止 Thinking、强制补答案或临时改采样绕过截断；这些会改变生成过程，应属于另一项研究配置。

## 5. Stage2：采集、选层与 A/B/C

通过新 smoke 后，固定生成器提示、采样、预算、后端、源码和 manifest，采集原 100 train、200 test。每题一条无干预参考轨迹，不检查、不反馈、不返工。

复用当前独立原始前缀重前向提取方法。输入只到该位置的确切原 token 端点，不重新分词，也不读取后续推理。保持当前输出层索引和末层 final norm 定义。先用当前可靠方法完成本轮，不同时引入新的 hidden 提取算法。

按当前 fit.py 的真实定义保留三组：

| 组 | 训练输入 | 标签 |
| --- | --- | --- |
| A | 完整轨迹末尾某层 hidden | 最终是否答错 |
| B | 各有效段落检查点末尾某层 hidden | 所属完整参考轨迹最终是否答错 |
| C | 检查点编号和前缀 token 数，不使用 hidden | 所属完整参考轨迹最终是否答错 |

A 冻结后仍可按现有代码在中途位置评估。B 每题全部位置的总权重为 1。C 是位置和长度对照，不是另一种 hidden 探针。

A/B 在训练题内部按题五折选择平均 AUROC 最高层；同题全部位置处于同一折，标准化只在该折训练数据上拟合。相同均值保留较小层号。沿用 L2 逻辑回归 C=0.1、max_iter=2000；冻结后才评价测试题。

保留 AUROC、前 1/2/3 个有效位置和全体中途位置统计；另报固定 0.5 阈值的 Accuracy、Balanced Accuracy、Precision、Recall 以及全部预测最终答对的基线。按题等权，bootstrap 1000 次。探针分类准确率与模型解题正确率分开。

100/200 是固定题数，不保证每题都有可用数学标签：
- 截断、格式/评分异常保留记录，标签为缺失，不随意标成数学答错，不换题。
- 报告 train/test 全队列的正常完成率、可评分率和正确提交比例；正确提交比例的分母包含未完成题。
- 探针指标只针对具有确定标签与所需特征的题，同时报告覆盖率和排除原因，不能外推到全部请求。
- 训练任一类别不足五折条件时给出不足报告，不借测试题；测试单类别时 AUROC 为 NA。

固定 300 道采集完成且数据允许拟合时，交付 A/B/C 探针与 Stage2 报告。验证器尚待人工核验不能阻塞这一步。

## 6. 验证器：先比较两种模式，再冻结一种

仍用 Qwen3.5-9B，BF16。它在这里是通过提示词承担验证任务的通用模型，不能因为基模较新就宣称其判断可靠。

预先限定两个候选，不做大规模搜索：

| 候选 | 模式 | 每次输出上限 | 采样 |
| --- | --- | --- | --- |
| 直接判断 | enable_thinking=False | 1024 token | temperature=0.7、top_p=0.8、top_k=20、min_p=0、presence_penalty=1.5、repetition_penalty=1 |
| Thinking 检查 | enable_thinking=True | 16384 token | temperature=1.0、top_p=0.95、top_k=20、min_p=0、presence_penalty=1.5、repetition_penalty=1 |

两组都 do_sample=True。非 Thinking 采样采用官方通用起步建议，仍需实测数学验证质量。16384 是应对旧 4096 大量截断的固定开发候选，不保证足够；这轮不继续无限增大。

每次验证输入上限 147456 token，以验证器实际 tokenizer 编码计数，包含题目、全部前缀、外部编号和提示。直接判断总上下文上限 148480；Thinking 检查总上下文上限 163840。它们是运行预算，正式前检查驻留显存与后端支持，不截掉早期推理适配长度。

代码中目前 input_ids 硬编码 enable_thinking=True、verify 使用生成器 sampling_config、parse_verdict 强制一个 </think>。需要在现有位置一起修正：
- 验证器 mode 和 sampling 从自己的配置读取，不影响 4B 的 Thinking 和采样。
- Thinking 模式严格解析其关闭 Thinking 后的最终 JSON；非 Thinking 模式严格解析整个生成响应中的最终 JSON。
- 依据实际原生 template 验证包装，不从任意文本搜第一个 JSON，不把未结束 Thinking 当成已完成。
- 两组都正常 EOS 后接受完整 JSON；截断、格式错误保持 UNCERTAIN，并单列原因。
- 验证器 RNG 与生成器独立；以题目、完整编码输入、模式和检查类型派生，HIGH/LOW 路径名不进入种子。

先复用已有正确、错误和终点合成控制各一例，检查两种模式的输入、JSON 和编号；合成控制只测接口，不作为真实数学准确率。

### 验证范围与输出

只输入 problem、当前实际完整前缀、外部检查点编号、保留反馈和 intermediate/terminal 类型。不能输入标准答案/解答、未来推理、探针分数或路径名。原始引用中的 chat 控制标记采用已验证的安全文本视图，保留数学内容、原偏移和输入哈希。

检查截至该位置仍被采用的数学断言、计算、假设和推导。明确假设、探索分支、已撤回错误和自我纠正不自动判 FAIL。中途未完成整个证明或没有最终答案不自动判错；终点则需检查答案有推导支持、条件覆盖与完整性。

外部“检查点编号”是段落编号，段落不保证等于一条完整数学步骤。不要把文内编号当作外部编号；切断断言而无法确认时用 UNCERTAIN。

两组使用相同判决语义和最终 JSON：
~~~json
{
  "verdict": "FAIL",
  "first_error_step": 4,
  "diagnosis": "A concrete unresolved error in the current reasoning.",
  "hint": "A specific next action for correcting that error."
}
~~~

这个例子只展示格式。PASS 的 first_error_step=null、diagnosis/hint 为空；UNCERTAIN 的 first_error_step=null、hint 为空，可填原因；FAIL 必须定位当前未解决错误，并给出有效编号与具体 diagnosis/hint，各不超过 300 字符。

严格校验字段、枚举、类型、编号、重复键和长度。保留 raw/effective 判决。FAIL 指向已有 PASS 前缀时沿用 checkpoint_conflict→UNCERTAIN，记录风险，不能声称该 checkpoint 已被证明无错。只将完整 diagnosis/hint 加入生成器，不加入验证器自己的整段 Thinking。

### 开发选择与独立核验

在固定 20 道 verifier_dev 上采集新生成器的无干预参考轨迹。每题最多取三个不同输入：早期中途、后期中途和终点；用已有确定性位置抽取，不用 B 分数，不按验证器预测筛输入。两种候选检查同一批输入。

人工确认当前有效推理是否有未解决错误，并记录位置；可离线参考标准解答。模型自评与最终答对都不能代替过程标签。没有人工标签时先完成两组的接口、完成率和成本比较，交付待核验表，继续 Stage2 的独立工作；不能宣布选定可靠验证器。

本轮只用开发集选择模式：
- 至少有 10 个可判定正确前缀和 10 个可判定错误前缀，才做初步模式选择。
- 候选要求：错误前缀被判 PASS 的比例≤20%，正确前缀被判 FAIL 的比例≤20%，所有输入的 UNCERTAIN/格式失败/截断比例≤20%，并且 Balanced Accuracy≥80%。这里的 Balanced Accuracy 是正确前缀被判 PASS 的比例与错误前缀被判 FAIL 的比例的平均；UNCERTAIN 在所属真值类别中计为未正确判断。各比例按题等权，另报原始计数。
- 只有一组达标，选该组；两组达标，选平均完整调用耗时更低的一组（所有输入，含失败调用），同时报告质量差异；两组都不达标，报告验证器失败，不启动正式 Stage3。
- 参数、提示和预算在开发阶段固定；这轮不增加投票、工具执行或新 PRM 训练。

随后仅对选定模式使用原 20 道 verifier_audit 独立核验。要求至少 20 个可判定正确前缀、20 个可判定错误前缀，沿用上述质量门槛。标签数不足时，从未用于正式 train/test 的剩余题中按事先固定顺序追加开发/核验题；所有追加输入都纳入报告，不挑有利样本，两个集合继续隔离。

独立核验失败不能在同一 audit 集上换另一组再“通过”；新的验证器配置要用新的独立核验集合。门槛是探索实验的工程标准，不是公认可靠性认证；报告样本量、按题等权指标和按题 bootstrap 区间。

另报告 Balanced Accuracy，UNCERTAIN 按未完成判断处理，不从准确率分母删去；人工无法判断的输入单列。对每道核验题固定抽一个前缀，用第二个独立验证种子复查，以报告判决一致率，正式路径仍只检查一次。

计时从验证器输入 prefill 开始，包括 Thinking/JSON 输出，不能只报 decode_seconds。报告每次输入输出 token、平均时间及分位数；不得把旧 6 次 PASS/21 当作准确率。

## 7. Stage3：完整快照与同题 HIGH/LOW

先完成生成器和验证器模式的必要代码分支，再冻结 Stage2 源码，避免采集中途频繁改共享 inference.py。验证器开发只调整其独立配置；模式选定后写入 stage3 配置并建立新的 Stage3 run。

Stage3 读取新 stage2_run 和 probe_B.json，不硬编码旧第 19 层。同一条无干预测试参考轨迹按 B 的线性输出 z 选最大/最小有效位置，同分选最早。需要至少两个不同有效中途位置；最终数学对错不参与选择。

明确记录资格：固定 200 道测试题中有哪些参考轨迹可正常评分、有哪些至少两个候选、哪些满足首检前复现。缺少资格的题与原因保留。正式统计报告实际配对题数，不把有效子集冒称全部 200 题。

每题 HIGH/LOW 两条独立请求，交替执行顺序，均从新 prompt 开始。首检前共享参考记录的原种子和有效采样，要求逐 token 对齐；不一致时保留诊断，不能靠重新采样参考消除差异。

1. 所选位置检查一次。
2. PASS：保存最近通过位置的完整状态，继续生成；不向生成器追加 PASS 提示。
3. FAIL：恢复最近 PASS 的完整状态，再追加固定包装的具体反馈，续写；没有 PASS 则恢复 prompt。
4. 中途 UNCERTAIN：继续，但不保存 PASS 检查点。
5. 此后只做终点检查和必要返工；终点 PASS 才提交，终点 UNCERTAIN 终止为未验证。
6. 首次中途检查后不再按新轨迹 B 分数选另一主动位置。

### 混合缓存恢复

沿用已实现的 full_state_snapshot：
- 两份不可修改快照：prompt 和最近 PASS；加一份活跃状态。
- 包含各层 K/V、卷积/递归状态与初始化标志、原 token 前缀、位置、logits 和必要 Thinking/段落解析信息。保持状态原 dtype，不强制把 float32 递归状态转为 BF16。
- 恢复时深拷贝快照为活跃状态，不能直接让前向修改快照。权重共用，不复制模型。
- 快照必须停在确切原 token 端点，不含未检查未来 token；必要的 pending token 补前向与边界重建计费。
- 失败后不退回已消费 RNG，不重置累计预算；暂停对照则复制相同 RNG 状态。
- 不使用 cache.crop 代替线性注意力状态恢复。

生成不同失败后缀、恢复同一快照，再喂相同反馈与测试 token：比较各层状态和 logits，并与未生成失败后缀的克隆对照比较；另与精确前缀重算对照比较。沿用锁定容差、报告原始误差，不扩大容差掩盖后缀残留。新长前缀也检查，不只用随机小模型结果代替官方权重检查。

若恢复只能依赖全前缀重算，明确标为重算模式，不宣称缓存复用。暂不增加每 token 快照、递归逆运算或自定义 kernel。

### 路径预算与计时

| 项目 | 新固定上限 |
| --- | --- |
| 每次生成器尝试的新 token | 81920 |
| 生成器总上下文 | 131072 |
| 每条 HIGH/LOW 路径累计生成器新 token | 163840 |
| 每条路径验证器调用 | 4 次 |
| 每条路径回滚 | 2 次 |
| 验证器输入 | 147456 token |
| 验证器输出与总上下文 | 由已冻结模式确定，见第 6 节 |
| 所有非 decode 前向输入累计 | 1048576 token |

所有真实计算，包括被撤销输出、失败验证、反馈 prefill 与 checkpoint 边界重建，都计预算。达到预算终止，不临时加额外检查或改变判断规则。

T_request 从 prompt prefill 到提交/终止，含生成、验证器全部计算、快照建立/复制/恢复、反馈前向和原有路径持久化；加载、参考轨迹采集、离线特征和标准答案评分另报，不算路径时间。CUDA 同步计时。

两模型在 Stage3 同 GPU 驻留、串行执行；每次检查后释放验证器请求 cache。按新最大长度与冻结验证模式重新检查显存；旧 64K/4096 的容量通过不能代表新上限。若 OOM，仅在正式前降低 prefill 块并重新验证；不能运行中量化、缩短前缀、丢快照或自动换模型。内在驻留容量仍不足时交付明确容量诊断，保留 Stage2 成果。

因算法预算、格式、验证器输入限制或 UNCERTAIN 而正常终止的路径，正确提交指标 Y=0，独立记录原因；这与 Stage2 的缺失数学标签不同。基础设施故障单列，恢复配对计算，不根据哪条路径失败删题。

## 8. 启动条件、报告与执行顺序

正式 Stage2 的条件仅是第 4 节的新 smoke、格式、预算和真实模型检查；不等待验证器独立人工核验。

正式 Stage3 的条件是：
- 新 B 已冻结，独立验证器核验通过；
- 4 道真实 HIGH/LOW pilot 完整结束，覆盖可解释的判决与终止；不能用强制 PASS/FAIL 伪装真实效果；
- 新长度下完整缓存恢复、首检前复现与两模型容量检查通过；
- 配置、提示、源码、精度和预算已冻结。

只补最小必要测试：最终响应带解释/重复 Final/嵌套 boxed/截断，两个验证器模式的严格 JSON 与独立 RNG，以及新长度下缓存与显存。复用现有 tests，不新增测试框架，不因每次保存又重复全部 GPU 检查。

执行顺序：
1. 读取当前分支、规则和现有诊断，确认没有重复后台任务；保留已下载模型与环境。
2. 一次完成共享最终答案解析、生成提示/预算、验证器独立配置/解析和计时的必要改动，跑受影响 CPU 检查。
3. 建立新的 Stage2 run，跑原固定 10 题 smoke。通过后冻结、开始固定 300 题采集并拟合 A/B/C。
4. 在独立配置中完成两个验证器候选的接口和固定开发题比较。可与 Stage2 准备工作交错进行，同一 GPU 不并行抢占显存。
5. 人工标签未就绪时生成一份待核验表，继续所有不依赖标签的工作。一次说明所需标签；不得把此状态写成等待最终格式许可。
6. 开发选定模式、独立核验通过后，固定 Stage3 配置，执行 4 题 pilot，再执行合格测试题的 HIGH/LOW。
7. 更新 Stage2/Stage3 README、状态与报告，沿用已有原子保存、resume、Git/LFS 备份。改变正式配置或源码时保存旧 run，建立新身份，不混用结果。

复用原两份配置路径：
- stages/stage2/qwen35_4b_omni_config.json
- stages/stage3/qwen35_4b_omni_high_low_config.json

根据实际 --help 使用现有 probe、verifier review、high-low prepare/pilot/freeze/test 入口；不要新增一套编排程序。stage3 配置中的 stage2_run 必须更新到新 Stage2 的真实路径，两个候选配置只作为开发诊断保存。

最终报告至少包含：
- Stage2 固定队列完成/可评分覆盖率，数学正确率、A/B/C 结果和各类排除原因。
- 两种验证器开发结果，选定理由、独立核验质量/一致率/耗时及样本量。
- Stage3 合格题数、各路径正确提交率和平均 T_request、按题配对差及 95% bootstrap 区间。
- 生成/验证 token 与耗时、调用/回滚/终止原因、快照成本和峰值显存。
- 段落检查点数量、最长间隔、near_end 分布，明确不保证每个段落等于完整数学步骤。

当前这轮只检验单请求的离线 HIGH/LOW。没有证据时不得宣布在线加速、多请求吞吐改善、验证器普遍可靠，或把换模型、换题集后的差异归因于一个单独因素。
